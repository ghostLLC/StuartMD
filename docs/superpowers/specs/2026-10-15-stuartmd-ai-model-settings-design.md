# StuartMD AI 模型配置设计

日期：2026-10-15。适用代码基线：3.5.12，提交 4b83005a90b7517d5f9eedd47a5b42cc0c2eb35d。

## 1. 使用目标

普通用户选择厂商、填写 API Key、勾选模型，即可保存多个模型。日常从跨厂商的已保存模型列表直接选择。模型名称、官方地址、接口参数、容量和计数方式由软件准备。

用户已经确认预置当前官方型号、多模型保存、直接选择模型及简洁设置页面的设计方向。依赖 computer use 的窗口、浏览器和视觉检查按照用户指令记录为 SkippedByUser。

## 2. 设置页面

AI 设置按顺序显示“已保存模型”“服务商连接”“对话偏好”。沿用现有主题颜色、字体和控件尺寸。

### 2.1 已保存模型

每个模型显示为独立条目：

- 主要文字：模型显示名称。
- 辅助文字：服务商、服务区域、实际 API 模型名称。
- 状态文字：当前选择、默认模型、尚未验证、验证通过、配置缺失、服务不可用或模型已下线。
- 操作：选择模型、编辑、设置默认、停用、删除。

提供搜索和“添加模型”按钮。首次使用显示添加入口和简短说明。列表支持键盘操作，状态同时使用文字表达。窗口变窄时辅助信息和操作换行，模型名称保持可读。

“当前选择”和“默认模型”分别保存。当前选择用于下一次提问；默认模型用于没有历史选择的新环境。用户已经选择的模型发生停用、删除或失效时，要求明确选择后续模型。

### 2.2 添加模型

1. 选择 DeepSeek、通义千问、Kimi、智谱或自定义 OpenAI 兼容服务。
2. 显示该连接的密钥保存状态。已有密钥直接使用；缺少密钥时提供一个密码输入框。阿里云等存在不同服务区域的厂商使用区域选项。
3. 显示可搜索、可多选的模型目录。每个模型显示名称、适用说明、上下文容量和支持的思考方式。
4. 点击“添加所选模型”，一次保存连接和模型条目，添加结果进入已保存模型列表。连接首次建立时，首个添加的模型成为当前选择和默认模型；后续添加保留已有选择。

重复添加相同连接和相同 API 模型名称时定位已有条目，保留其参数。普通添加过程无需填写 Base URL、模型名称、Token 计数 JSON 或资源路径。

自定义服务提供名称、地址和模型名称输入。高级参数包含容量、计数方式和请求选项，采用有名称、有范围校验的字段。缺少必需配置时显示具体缺项并保留填写内容。

取消编辑丢弃本次未保存输入。保存失败保留本次输入。切换厂商前明确处理未保存输入。设置页面定时刷新和其他窗口更新均不得覆盖正在编辑的内容。

### 2.3 服务商连接

连接条目集中管理服务区域、地址、密钥保存状态和关联模型数量。同一个连接的多个模型共用一个加密密钥。

官方连接使用对应区域的固定地址。自定义地址修改沿用现有新主机确认规则。密钥输入完成保存后立即清空输入框；读取配置只返回保存状态。

删除单个模型保留其连接和密钥。删除连接列出受影响的模型，确认后删除对应模型并清除凭据。影响活动请求的连接或凭据修改先结束相关请求，再提交修改。

### 2.4 对话偏好

回答长度、语气、自定义风格、选区快捷键、默认材料范围和记忆偏好保留在此区域。模型的思考参数、输出容量和计数设置归属各自模型条目。

## 3. 模型目录

目录由后端统一读取，前端通过配置接口取得。目录文件包含 schema_version、catalog_version、verified_at、来源链接和模型条目，随程序发布。使用 JSON 及 serde_json 解析并验证结构。

### 3.1 已核对的官方型号

| 厂商 | 显示名称与 API 模型名称 |
| --- | --- |
| DeepSeek | DeepSeek V4.1 Flash：deepseek-flash；DeepSeek V4 Pro：deepseek-v4-pro |
| 通义千问 | Qwen3.8 Max：qwen3.8-max；Qwen3.8 Flash：qwen3.8-flash；Qwen3.7 Plus：qwen3.7-plus |
| Kimi | Kimi K3：kimi-k3；Kimi K2.6：kimi-k2.6；Kimi K2.7 Code：kimi-k2.7-code；Kimi K2.7 Code Highspeed：kimi-k2.7-code-highspeed |
| 智谱 | GLM-5.3：glm-5.3；GLM-5.3 Flash：glm-5.3-flash；GLM-5.3 FlashX：glm-5.3-flashx |

以上型号来自 2026-10-15 核对的官方目录。账号权限、服务区域和软件支持能力分别核验。

### 3.2 模型条目

每个目录模型声明：厂商类型、区域、API 名称、显示名称、协议、输入输出类型、流式能力、结构化输出能力、思考开关、可选推理强度、默认参数、上下文上限、输入上限、输出上限和计数配置。

思考能力按具体模型声明。例如 Kimi K3 和 GLM-5.3 提供 low、high、max 三种推理强度，并始终开启思考。前端根据能力显示相应控件，后端验证用户选择并生成请求参数。

Token 计数配置与具体模型及版本绑定，包含官方计数接口或官方 tokenizer 资源、消息模板和资源指纹。每个内置模型必须同时具备经核对的容量和计数资料。目录中的多模态能力只作为能力信息；StuartMD 当前发送的文本材料继续使用现有正文和 PDF 提取流程。

### 3.3 目录刷新

明确支持模型发现接口的连接显示“刷新模型目录”。刷新结果包含实际模型名称和厂商返回的元数据，记录获取时间。网络失败显示实际错误，保留本地已保存目录和模型。

在线目录和软件内置目录分别标注来源。仅返回模型名称的接口只能证明目录中存在该名称；模型容量、计数和参数需要对应的已验证配置。

更新目录保留用户模型编号、用户显示名称、用户参数及当前选择。新增型号供用户添加；已下线型号显示替换入口，由用户选择目标型号。

## 4. 日常选择模型

顶部模型入口和伴读输入区共用一个选择组件。展开后直接显示全部已保存模型，提供搜索，最近使用的模型优先显示，默认模型有明确标记。服务商名称作为条目辅助信息。

选择后立即保存 active_model_id 和最近使用信息，关闭选择框并更新两个入口的名称。配置不完整的条目显示具体原因和设置入口，保持可见。

模型选择、目录刷新和编辑表单分别持有状态。选择模型只提交选择操作，编辑模型只提交该条目变更，避免提交旧表单覆盖其他设置。

模型列表、默认模型、上次选择及最近使用顺序在重启后恢复。其他窗口取得更新事件后刷新列表和当前选择。已经发送的请求保持其模型、参数和密钥快照，新的选择用于后续请求。

## 5. 配置数据

### 5.1 保存结构

AI 配置升级为明确版本的结构，保留既有问答和记忆偏好，并包含：

| 字段 | 含义 |
| --- | --- |
| providers | 连接数组：id、type、label、region、kind、base_url、enabled、builtin、credential_ref、credential_revision |
| models | 模型数组：id、provider_id、model_id、display_name、catalog_id、catalog_version、enabled、thinking、max_output_tokens、token_counting、overrides |
| active_model_id | 当前模型编号，可为空 |
| default_model_id | 默认模型编号，可为空 |
| recent_model_ids | 按最近使用顺序保存的模型编号 |

模型 id 使用稳定 UUID，编辑显示名称和参数保持编号。provider_id 引用已存在的连接，model_id 是实际发送的 API 名称。目录编号和 API 名称分别保存。

密钥继续使用 Windows DPAPI 保存。credential_ref 对应本机凭据标识；配置、文档、日志、归档上下文和列表响应均不得包含密钥明文。

### 5.2 旧配置迁移

迁移在原生端持有设置锁时执行，一次性原子保存。每个已有服务商的非空 model 转为一个模型条目，保留名称、地址、思考参数、输出预算和 token_counting。active_provider_id 对应的模型成为 active_model_id 和 default_model_id。

迁移保留原有密钥文件和服务商编号。空白自定义配置保留为连接，等待添加模型。已有但已下线的名称继续显示对应条目及迁移提示。重复加载保持相同模型编号，拒绝写入未来版本配置。

### 5.3 并发保存

修改请求携带 expectedRevision，原生端在同一设置锁内比较版本并提交。版本变化返回 SettingsVersionConflict，前端保留当前输入并提供重新加载入口。

配置保存、选择模型、默认模型修改、凭据修改和目录刷新使用各自原子操作。成功提交后发布 ai-config-changed，事件包含 revision、受影响编号和变更类别。

## 6. 请求配置与验证

原生端以 modelConfigId 解析模型和连接，形成冻结的请求配置：连接编号、厂商类型、实际模型名称、地址、思考参数、输出预算、计数配置身份、目录版本和设置版本。

正文问答、快速问答、上下文预览、摘要和记忆整理使用同一个解析过程。模型选择在前端显示的名称必须对应后端解析结果。历史归档保留实际发送时的模型信息，模型条目删除后仍可查看已有回答。

按模型能力生成具体参数。需要在多轮调用中保留完整 assistant 内容或 reasoning_content 的模型，按照官方协议保存并传递相关字段；这些字段按照对应计数方式参与容量校验。结构化整理请求也遵守所选模型的思考和 JSON 能力。

“获取模型目录”与“验证模型回答”分别操作和记录。验证模型回答包含配置检查、计数检查、发送简短测试消息、接收实际正文、核验完成标记和实际 usage。页面注明会发送测试消息。验证通过记录模型配置身份、凭据版本和时间。

地址、模型名称、计数资料、思考参数、输出预算或密钥发生修改后，相关验证记录失效。验证失败保留已保存配置并显示失败阶段及具体原因。

## 8. 验收要求

1. 新用户添加内置模型时，只需选择厂商、必要区域、填写密钥和勾选模型。
2. 同一厂商保存两个以上模型，切换和编辑其中一个保持其他模型配置。
3. 不同厂商的模型同时出现在顶部和伴读的选择列表中，两个入口显示相同当前模型。
4. 关闭进程后重新读取真实设置文件，模型编号、顺序、默认模型和当前选择保持一致。
5. 已有配置迁移保留原模型、参数、加密凭据、会话和记忆，重复打开保持相同数据。
6. 活动请求期间选择其他模型，原请求继续使用发送时的配置，后续请求使用新选择。
7. 多个窗口同时编辑、删除当前模型、清除连接凭据、目录获取失败及模型下线均显示可操作的实际状态。
8. 目录取得成功和模型回答验证成功分别记录，缺少计数配置或实际正文时停止对应请求。
9. 使用现有 DeepSeek 凭据执行真实模型选择与调用验证；其他厂商的在线检查依据实际凭据记录范围。
10. 运行项目已有检查及本次问题对应的回归检查。依赖窗口或视觉操作的检查记录为 SkippedByUser。
